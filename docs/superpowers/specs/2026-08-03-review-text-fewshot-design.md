# 설계: 후기 텍스트 판정 few-shot 예시 추가

- 문서 버전: v1.0
- 작성일: 2026-08-03
- 상위 문서: [2026-07-23-judgment-engine-design.md](./2026-07-23-judgment-engine-design.md)
- 이 문서의 범위: `buildPrompt()`가 Gemini에 보내는 프롬프트에 **후기 텍스트(상담 후기/시술 후기 내용) 판정 few-shot 예시**를 추가한다. 사진 판정 개선은 별도 스펙으로 다음에 진행한다(비목표).

## 왜 필요한가

실사용 스모크 테스트(Task 19) 결과 확장이 정상 동작하는 것은 확인했지만, 텍스트 판정 정확도 자체는 아직 검증/보강되지 않았다. `buildPrompt()`는 현재 승인/보류 "기준 문구"만 담고 있고(의미불명 예시로 `ㄱㄴㄷㄹㅁ`, `★★★★★★★★★` 같은 명백한 케이스만 인라인 포함), 실제 애매한 경계 케이스 — 부정적이지만 시술과 관련된 정상 후기, 잡담이 섞인 후기 등 — 에 대한 판단 기준이 모델에 충분히 전달되지 않는다. 관리자 화면에서 실제 승인/보류된 후기를 훑어본 결과(개인정보 때문에 원문은 기록하지 않음), 명백한 케이스는 기존 문구로 이미 커버되고 있고, 개선 여지는 **경계가 애매한 케이스**에 있다는 것을 확인했다.

## 1. 목표 / 비목표

**목표**
- `buildPrompt()`가 만드는 프롬프트에 후기 텍스트 판정용 few-shot 예시 섹션을 추가한다.
- 예시는 실제 후기 원문이 아니라, 관찰한 패턴을 각색한 문장으로 작성한다(개인정보/실제 고객 데이터를 코드에 남기지 않음).
- 애매한 경계 케이스(부정적이지만 유효한 후기, 잡담 섞인 후기 등)를 승인/보류 양쪽 예시로 포함해 기준을 명확히 한다.

**비목표**
- 사진(포토) 판정 개선 — 다음 스펙에서 별도로 다룬다.
- 실시간/동적 예시 수집(관리자 DB에서 매 요청마다 실제 사례를 긁어와 프롬프트에 넣는 RAG 방식) — 정적 큐레이션이면 충분하고 인프라 추가는 과함(YAGNI).
- 평가용 정답 데이터셋 구축(정확도 측정 자동화) — 이번 스펙은 프롬프트 보강만, 측정은 별도 논의.

---

## 2. 아키텍처

```
proxy/src/
├── prompt.ts            # 기존 — buildPrompt()가 promptExamples.ts를 가져다 조합
└── promptExamples.ts     # 신설 — 각색된 few-shot 예시 목록 (승인/보류)
```

- `promptExamples.ts`는 `judgment-engine`이 아니라 `proxy/src/`에 둔다 — 실제 Gemini 프롬프트를 만드는 코드(`prompt.ts`)와 같은 위치. `judgment-engine`은 프록시 URL만 알면 되는 순수 계층이라는 기존 원칙(§2, judgment-engine 설계 문서)을 유지한다.
- 예시는 코드 상수 배열이다. 별도 파일/DB 로딩 없음 — 한 줄이면 되는 걸 설정 시스템으로 만들지 않는다(YAGNI).

## 3. 데이터 형식

```ts
// proxy/src/promptExamples.ts
export interface PromptExample {
  label: 'APPROVE' | 'HOLD';
  text: string;      // 각색된 예시 후기 문장
  reason: string;    // 왜 이 판정인지 한 줄 설명
}

export const TEXT_JUDGMENT_EXAMPLES: PromptExample[] = [
  // 승인 — 부정적이지만 시술 경험에 대한 유효한 후기 (감정과 무관하게 승인)
  { label: 'APPROVE', text: '기대했던 것보다 꼼꼼한 느낌은 아니었어요.', reason: '불만이어도 시술 경험에 대한 구체적 내용 — 관련성 있음' },
  // 승인 — 짧지만 시술 관련 핵심 언급이 있는 후기
  { label: 'APPROVE', text: '통증 거의 없었고 직원분들도 친절했어요.', reason: '짧아도 시술 경험(통증)과 병원 응대를 구체적으로 언급 — 승인' },
  // 승인 — 잡담이 섞였지만 시술 관련 내용이 함께 있는 후기
  { label: 'APPROVE', text: '날씨도 더운데 오늘 시술받고 왔어요. 다운타임 없어서 좋았습니다.', reason: '잡담이 섞여 있어도 시술 관련 내용이 포함되어 있으면 승인' },
  // 보류 — 시술과 무관한 내용만 있는 경우
  { label: 'HOLD', text: '오늘 점심 뭐 먹지 고민되네요.', reason: '시술과 전혀 무관한 잡담만 있음 — 관련없음으로 보류' },
  // 보류 — 의미를 알 수 없는 반복 문자 (기존 프롬프트 문구의 예시와 동일한 결)
  { label: 'HOLD', text: 'ㅁㄴㅇㄹㅁㄴㅇㄹㅁㄴㅇㄹ', reason: '의미를 알 수 없는 반복 문자 — 보류' },
];
```

- 승인 3개(부정적이지만 유효 / 짧지만 유효 / 잡담+유효 혼합) + 보류 2개(무관한 잡담만 / 의미불명) — 총 5개로 시작한다. 개수를 늘리는 건 나중에 실사용 결과 보고 부족한 경계 케이스가 보이면 추가한다(YAGNI, 처음부터 많이 만들지 않음).

## 4. `buildPrompt()` 변경

기존 프롬프트의 "[승인 기준 - 후기 내용]" 문단 뒤에 예시 섹션을 추가한다:

```
[참고 예시]
${examples.map(e => `- "${e.text}" → ${e.label === 'APPROVE' ? '승인' : '보류'} (${e.reason})`).join('\n')}
```

사진 관련 문구(`[승인 기준 - 사진]`)는 이번 스펙에서 건드리지 않는다.

## 5. 테스트

- `proxy/tests/prompt.test.ts`에 케이스 추가: `buildPrompt()` 결과에 예시 섹션과 각 예시 문장이 포함되는지 확인.
- 기존 `judgeReview`/`engine.test.ts` 등은 프롬프트 내용에 의존하지 않는 mock 기반 테스트라 영향 없음 — 별도 회귀 확인 불필요.

## 6. 마일스톤

| 단계 | 내용 |
|---|---|
| M1 | `promptExamples.ts` 작성 + `buildPrompt()`에 예시 섹션 결합 + `prompt.test.ts` 보강 |
| M2 | 실사용 확인 — 애매한 경계 케이스 몇 건을 실제로 판정시켜보고 기준이 개선됐는지 육안 확인 |

M2까지 확인되면 사진(포토) 판정 개선을 다음 스펙으로 브레인스토밍한다.
